# 第五章 评估与可视化设计

## 5.1 引言

前文已经完成了扩展有限状态机推断方法的设计与实现，但仅给出模型结构并不足以证明方法的有效性。一方面，工业协议流量往往存在报文截断、会话不完整、字段变化复杂等特点，若仍采用“是否到达终态”这一单一二值指标，容易将结构正确但局部守卫尚不稳定的模型整体判定为失败；另一方面，本文所实现的系统不仅包含 EFSM 推断，还进一步在其上构建了概率扩展状态机（P-EFSM）及其 Web 可视化平台，因此需要从行为重放、结构匹配、约束语义与工程交互四个层面形成一套完整评估体系。

结合项目实现，本文评估模块由 `protocol_infer/evaluation` 与 `protocol_infer/visualization` 两部分共同支撑。其中，`run_evaluation.py` 负责完成“数据读取—训练/测试划分—FSM/EFSM 构建—多维指标计算”的完整流程；`efsm_evaluator.py` 实现了面向协议先验知识的增强型评价指标；`replay.py` 则提供了与前端展示一致的重放统计逻辑。基于上述实现，本章围绕数据选取与准备、评估指标设计、实验结果分析以及 Web 可视化系统设计四个部分展开论述。

## 5.2 数据选取与准备

### 5.2.1 数据来源

本项目的数据集统一存放于工程根目录下的 `Data/` 目录中，涵盖 MODBUS、DNP3、IEC104、S7COMM、EtherNet/IP、MQTT 等多类工业协议。考虑到增强型评估需要依赖协议规范级 Ground Truth（GT）信息，本文在正式量化评估中选取了当前代码中已经实现 GT 规范的三类协议作为主要实验对象，即 MODBUS、DNP3 与 IEC104。三者分别对应 `protocol_infer/evaluation/gt_guard_action.py` 中的协议知识库，以及 `run_evaluation.py` 中注册的监督标签器。

在系统实现中，数据读取采用 `PCAPPipeline` 完成，随后通过 `filter_events_for_protocol` 过滤非目标协议事件，并基于五元组与分段标识构建会话。为避免单个超大文件对训练效率造成明显影响，代码中将单个 PCAP 文件大小限制为 12MB，并通过 `max_pcaps` 控制参与训练的数据文件数量。该策略能够在保证样本代表性的同时控制实验耗时。

### 5.2.2 数据划分与预处理

在评估实现中，原始事件流首先按照 `SessionKey` 聚合为会话集合，然后依据 `test_ratio=0.2` 进行训练集与测试集划分。当原始会话数不足时，系统会调用 `_split_long_sessions` 将过长会话切分为多个片段，以保证训练与测试都具有足够样本量。若总会话数超过上限，则通过固定随机种子进行随机抽样，以减少不同实验间的随机波动。

与传统仅基于原始负载字节建模的方法不同，本文的数据准备包含两级抽象。

第一，控制流层利用 `ControlFlowPipeline` 对报文进行特征提取、聚类抽象与状态合并，形成离散符号序列。项目默认启用基于 Apriori 的伪字段发现机制，即 `AprioriFeatureExtraction.from_events(trace.events)`，用于从全局事件中识别具有区分性的关键字节位置，并据此构造消息抽象特征向量。

第二，数据流层利用 `DataFlowPipeline` 复用控制流阶段产生的抽象器、特征器以及 Apriori 位置集合，提取守卫学习与动作学习所需的变量字典，确保 EFSM 构建阶段与 FSM 阶段的符号语义保持一致。该处理避免了“控制流抽象符号”与“数据流变量提取”之间的语义漂移问题。

### 5.2.3 本章实验数据配置

为了使实验结果具备可复现性，本文采用项目默认参数开展评估：`max_pcaps=6`、`max_sessions=200`、`test_ratio=0.2`、`seed=42`。其中，MODBUS 案例中实际参与训练的数据文件包括 `FC1-permit.pcap`、`Modbus.pcap`、`crash.pcap`、`modbus-encapsulated-transport.pcap`、`modbus-mask-write-register.pcap` 和 `modbus-read-write-multiple-registers.pcap` 六个文件。按照当前实现，共得到 200 个会话，其中 160 个用于训练，40 个用于测试。

除真实工业协议数据外，项目还提供了 `generate_synthetic_sessions()` 与 `compare_apriori_feature_vectors.py` 等脚本，用于构造受控样本并验证特征设计的有效性。本文在“模型优势分析”部分将结合该合成实验进一步说明 Apriori 特征在控制流抽象阶段的必要性。

## 5.3 评估指标设计

### 5.3.1 指标与设计原因

#### 1. 设计原则

本研究不采用“完整会话是否被模型接受”作为唯一评价标准，原因有三点。

其一，工业协议流量常来自真实网络抓包，存在连接建立阶段缺失、会话被截断、链路重传以及跨设备异步交互等问题。如果严格要求每一条测试序列都必须从起始状态精确走到终止状态，则会将数据采集缺陷与模型推断误差混为一谈。

其二，EFSM 中的 guard 和 action 属于更细粒度的语义学习结果。实际实验表明，只要其中某一条 guard 判定失误，就可能导致整条会话在严格重放中被立即拒绝，从而掩盖控制流结构本身已经学习正确的事实。

其三，本文系统最终面向的是“协议行为解释”和“异常重放分析”场景，因此评价应首先反映模型对主流程的解释能力，再逐步考察其对状态结构、字段约束和变量更新的拟合程度。

基于上述考虑，本文采用“端到端行为重放为主、结构匹配为核心、约束语义为辅”的多维评价方案。

#### 2. 端到端重放与结构匹配指标

项目在 `protocol_infer/visualization/replay.py` 中定义了三种不同严格程度的匹配层级：

1. Replay Match：只要存在可执行边即可视为能够解释当前行为；
2. State Match：要求在当前状态下即可找到合法出边，不允许通过全局同符号重同步绕过结构错误；
3. Strict Match：不仅状态匹配，还要求 guard 判定通过。

在此基础上，本文选取如下主指标。

（1）会话平均匹配率 `session_state_step_match_rate`

该指标先对每个会话计算“状态级匹配步数 / 会话总步数”，再在所有会话上取平均。与简单统计“完整成功会话数”相比，该指标能够更平滑地反映模型在不同会话上的稳定性，对部分断链与局部漂移更为鲁棒，因此被本文作为最主要的结构评价指标。

（2）消息级结构匹配率 `step_state_replay_accuracy`

该指标统计全体消息步中满足状态级匹配的比例。其优点在于样本粒度更细，能够反映模型对局部行为单元的解释能力，适合作为会话级指标的补充。

（3）重同步步数 `steps_resynced`

当当前状态下不存在可执行边时，系统会在全局范围内寻找同符号候选边进行重同步。重同步步数越多，说明模型虽然能够“解释行为”，但结构定位能力较弱。因此，`steps_resynced` 可以衡量模型对真实会话上下文的一致性保持能力。

上述三项指标共同构成了端到端结构重放指标组。其中，会话平均匹配率用于衡量整体稳定性，消息级结构匹配率用于衡量局部解释能力，重同步步数用于揭示结构漂移程度，三者相互补充，能够避免单一指标失真。

#### 3. Guard 字段级 P/R/F1

在 `protocol_infer/evaluation/efsm_evaluator.py` 中，`GuardFieldEvaluator` 将推断得到的 guard 字段集合与协议规范中的 GT guard 字段集合进行比较，并计算精确率、召回率与 F1 值。其定义如下：

\[
Precision=\frac{TP}{TP+FP},\quad
Recall=\frac{TP}{TP+FN},\quad
F1=\frac{2PR}{P+R}
\]

其中，TP 表示推断字段与规范字段交集中的元素数，FP 表示模型误引入的无关字段数，FN 表示漏掉的规范字段数。

选择该指标的原因在于，guard 的学习目标并非单纯接受或拒绝某条报文，而是识别“哪些变量真正参与了状态分支决策”。字段级 PRF 能够直接反映模型在分支条件语义上的覆盖情况，比仅看严格重放成功率更能揭示守卫学习的本质效果。

#### 4. Guard 违规率

`GuardViolationEvaluator` 在实际测试流量上逐步执行推断出的 guard，并统计“guard 存在但被真实数据违反”的比例。设总检查次数为 \(N\)，违反次数为 \(V\)，则 guard 违规率定义为：

\[
ViolationRate=\frac{V}{N}
\]

该指标用于回答一个关键问题：即使模型猜到了某些 guard 字段，这些 guard 在真实流量中是否稳定成立。若 guard 字段级召回较高而违规率也很高，说明模型虽然捕获到了部分分支字段，但约束表达仍不可靠。因此，违规率是对 Guard PRF 的必要补充。

#### 5. Action 覆盖率

`ActionCoverageEvaluator` 将模型 action 所涉及的变量集合与 GT 动作变量集合做 Jaccard 相似度比较：

\[
Jaccard=\frac{|A\cap B|}{|A\cup B|}
\]

其中，\(A\) 为模型预测动作变量集合，\(B\) 为协议规范中的动作变量集合。

之所以选用 Jaccard 而不是单纯使用准确率，是因为动作变量学习本质上属于集合匹配问题：模型可能多预测、少预测或者完全错预测某些变量。Jaccard 指标同时惩罚遗漏与冗余，更适合描述“变量更新范围是否合理”。

#### 6. 状态差分准确率

`StateDiffAccEvaluator` 比较“模型 action 预测的变量变化”与“由相邻报文观测到的实际变量变化”是否一致。该指标并不要求变量值完全精确一致，而是关注变量是否发生变化以及变化方向是否被正确捕获。对于工业协议中的事务标识、长度字段、确认序号等变量而言，这种“状态差分”度量更符合工程分析需求。

#### 7. 指标合理性验证

本文所采用的多维指标体系具有如下合理性。

1. 它与模型分层结构一致。控制流结构由重放与状态匹配指标评价，guard 规则由字段级 PRF 与违规率评价，action 规则由覆盖率和差分准确率评价，因此能够分别对应控制流层、数据流层和概率层的不同目标。
2. 它兼顾了鲁棒性与可解释性。宽松重放指标可减少因单条 guard 失误造成的整体失真，而字段级与变量级指标又能够进一步解释模型失效的原因。
3. 它能够通过实验直接证明必要性。后文的 MODBUS 结果显示，若仅使用传统严格重放指标，模型会被判为完全失败；但在状态级结构重放指标下，模型实际上已经能够较好解释主流程行为。这一结果反向验证了本文指标设计的合理性。

### 5.3.2 实验结果

#### 1. MODBUS 案例评估结果

第一，若采用传统严格回放指标，则该模型在 MODBUS 数据集上的 `trace_replay_acc` 为 0，看起来模型完全无效；但在本文提出的状态级结构匹配指标下，会话平均匹配率达到了 0.9902，消息级结构匹配率达到 0.9503，仅有 8 个步需要重同步。这说明模型已经准确学习到了大部分主流程结构，传统“全有或全无”的评估方法显然过于苛刻，无法真实反映推断效果。

第二，Guard 字段级召回率达到 0.6667，说明模型已经识别出大部分与状态分支有关的关键字段，但精确率仅为 0.1429，且 guard 违规率高达 0.9184。这表明当前 guard 学习仍存在明显的过拟合与冗余字段引入问题，数据流层约束学习仍是后续优化重点。换言之，本文方法在“控制流主干恢复”方面已经取得较好结果，但在“细粒度语义约束”方面仍有提升空间。

为了验证方法在不同工业协议上的适用性，本文进一步在 DNP3 与 IEC104 数据集上运行相同评估流程，结果如表 5-2 所示。

由表 5-2 可见，本文实现的模型在三类协议上都保持了较高的结构匹配能力，其中 MODBUS 与 DNP3 的会话平均匹配率均达到 0.9902，IEC104 也达到 0.8884。这说明基于消息抽象、PTA 构建、K-tail 状态合并与变量增强学习的整体流程具有较好的控制流泛化能力。

但从语义类指标看，不同协议之间差异明显。MODBUS 的状态差分准确率达到 0.5049，高于 IEC104 的 0.2241，而 DNP3 在当前实现下几乎未能形成有效的 guard/action 语义匹配结果。这说明：

1. 本文方法在恢复“协议主交互路径”方面较为稳定；
2. 协议语义字段映射、守卫约束学习以及动作变量提取的质量会显著影响增强型指标；
3. 多协议场景下的 GT 规范覆盖度与字段别名归一化质量，是后续改进的重要方向。

因此，从论文论证角度看，表 5-2 的意义不在于说明所有协议都已达到理想语义精度，而在于证明本文模型已经具备稳定的结构恢复能力，同时增强型指标能够清楚指出模型当前的不足位置，这正体现了多维评估体系的价值。

#### 3. Apriori 特征设计优势实验

为验证控制流层中 Apriori 伪字段发现机制的有效性，本文进一步运行 `test/evaluation_test/compare_apriori_feature_vectors.py`。该实验构造两类仅在关键字节位存在差异的合成消息，一组采用原始 `ControlFeatureExtraction` 特征，另一组采用 `AprioriFeatureExtraction` 特征，并使用相同的 KMeans 聚类器进行比较。结果如表 5-3 所示。

表 5-3 Apriori 特征向量对比实验结果

| 方法 | ARI | NMI | V-measure | Silhouette | Davies-Bouldin |
| --- | --- | --- | --- | --- | --- |
| 基线特征 `ControlFeatureExtraction` | 0.0000 | 0.0000 | 0.0000 | 0.0000 | 0.0000 |
| Apriori 特征 `AprioriFeatureExtraction` | 1.0000 | 1.0000 | 1.0000 | 0.9968 | 0.0048 |

该结果表明，当不同消息类型只体现在少量关键字段而非整体长度或方向信息时，传统统计型特征难以形成有效分离，而基于 Apriori 的伪字段发现可以准确捕获区分性位置，从而显著提升聚类质量。这一实验从侧面证明了本文在控制流抽象阶段引入 Apriori 特征的必要性，也是本文模型优于简单字节统计特征方案的重要依据。

#### 4. P-EFSM 概率层优势分析

在 EFSM 基础上，本文进一步通过 `PEFSMInferencer` 对训练会话进行重放统计，为每条转移记录访问次数 `traverse_count`、条件概率 `P(transition|src)` 与置信等级 `confidence`，从而构成 P-EFSM。以 MODBUS 为例，运行 `test/evaluation_test/eval_pefsm.py` 得到的结构统计结果如下：

1. 模型包含 15 个状态、19 条转移；
2. 存在 4 个分支状态，即同一源状态对应多条可能出边；
3. 在状态 `s10` 上，转移 `s10 --[C4]--> s2` 的观测概率为 0.9583，而 `s10 --[C3]--> s12` 的概率仅为 0.0417。

上述结果说明，引入概率层后，模型不再只给出“可能发生哪些转移”，还能够给出“这些转移在真实流量中的发生倾向”。这对协议行为解释具有两点优势。

第一，在可视化分析中，研究者可以优先关注高概率主路径，而将低概率边视为异常路径、罕见分支或特殊操作，从而提高分析效率。

第二，在回放和在线推演时，当同一状态下存在多条合法出边时，系统可优先选择概率较高的转移，减少随机选边带来的不稳定性。项目中的 `ReplayBuilder` 正是按照“guard 通过后优先选取概率最高的边”实现确定性重放，因此概率层对提升回放稳定性具有直接作用。

#### 5. 实验结果小结

综合以上实验，可以得到如下结论。

1. 本文模型在控制流结构恢复方面表现较好，尤其在 MODBUS 等协议上能够稳定重放主流程。
2. 多维评估体系能够有效避免传统严格指标的失真问题，并能进一步定位模型在 guard 和 action 语义学习上的薄弱环节。
3. Apriori 特征设计在消息抽象阶段具有明显优势，是提升状态机结构质量的重要因素。
4. P-EFSM 的概率层为分支解释、路径排序和稳定重放提供了额外信息，使模型更适合后续可视化分析与工程应用。

## 5.4 Web 可视化

### 5.4.1 后端设计

本文在 `protocol_infer/visualization` 模块中实现了基于 FastAPI 的 Web 可视化系统，其目标是将 P-EFSM 的训练、评估、序列化与重放分析能力以服务化方式对外暴露。整体后端可划分为四层。

第一层为接口层，由 `webapp.py` 定义 HTTP 路由并完成参数接收、异常处理与静态资源挂载。系统入口为 FastAPI 应用 `app`，同时通过 `StaticFiles` 挂载前端页面资源。

第二层为业务编排层，由 `VisualizationService` 负责核心逻辑，包括数据集发现、训练参数解析、PCAP 加载、训练/测试切分、P-EFSM 构建、指标计算、模型缓存与外部 PCAP 回放等。

第三层为模型与评估层，复用了前文实现的 `ControlFlowPipeline`、`DataFlowPipeline`、`ProbabilisticPipeline`、`run_full_evaluation` 与 `ReplayBuilder`。因此，可视化模块并非独立重写一套训练流程，而是对已有算法实现进行统一封装，这保证了“命令行评估结果”与“Web 页面展示结果”的一致性。

第四层为序列化与展示支持层，`PEFSMSerializer` 将状态、转移、概率、置信度、回放步骤以及指标结果转换为前端易于消费的 JSON 结构。

从工程实现看，该后端设计具有三个优点。

1. 复用性强。可视化系统直接调用已有训练与评估代码，避免了算法逻辑在不同模块中重复实现。
2. 支持多种数据模式。`VisualizationService.learn_from_dataset()` 同时支持 `pcap`、`synthetic` 与 `pcap+synthetic` 三种数据模式，既可面向真实流量分析，也便于教学演示与功能验证。
3. 支持交互式性能控制。系统预设 `fast`、`balanced`、`thorough` 三种训练配置，并可按概率或访问次数对 P-EFSM 进行剪枝，从而在响应速度与模型覆盖率之间灵活折中。

### 5.4.2 核心 API 设计

结合 `webapp.py` 的实际实现，本文 Web 系统的核心 API 如表 5-4 所示。

表 5-4 Web 可视化核心 API

| 接口 | 方法 | 功能 |
| --- | --- | --- |
| `/api/health` | GET | 服务健康检查 |
| `/api/datasets` | GET | 获取可用数据集列表及其模式信息 |
| `/api/learn` | POST | 基于指定协议与数据集训练 P-EFSM，并返回模型、回放结果与评估指标 |
| `/api/artifacts/{artifact_id}` | GET | 获取指定训练产物的模型、回放与指标信息 |
| `/api/artifacts/{artifact_id}/upload-pcap` | POST | 上传新的 PCAP 文件，并利用已有模型执行重放分析 |

其中，`/api/learn` 是系统的核心接口。该接口接收协议名、数据路径、最大 PCAP 数、最大会话数、训练配置、测试集比例、剪枝方式等参数，并在服务端完成以下流程：

1. 根据数据模式加载真实流量或生成合成会话；
2. 调用控制流层、数据流层与概率层完成 P-EFSM 训练；
3. 调用 `_build_metrics()` 统一计算重放指标与 Guard 指标；
4. 将模型、训练回放结果与指标打包为一个带 `artifact_id` 的产物返回前端。

`artifact_id` 的设计使系统具备轻量级状态管理能力。训练完成后，模型将以 `LearnedArtifact` 的形式缓存在服务端内存中，后续可以通过该标识反复查询模型信息，或对新的 PCAP 文件执行回放分析，而无需重复训练。这一设计提高了交互效率，也使 Web 平台具备“训练一次，多次分析”的使用模式。

`/api/artifacts/{artifact_id}/upload-pcap` 则体现了系统的工程应用价值。用户可将新的未知流量上传至后端，系统复用原训练阶段保存的 `DataFlowPipeline` 与 `ReplayBuilder`，先将新流量转换为抽象消息，再沿已有 P-EFSM 进行逐步重放，并返回每一步的匹配状态、对应转移、概率和备注信息。这样，研究者便可以直观观察新流量是沿主流程运行、发生了重同步，还是在某个状态点无法匹配，从而辅助异常分析与模型诊断。

### 5.4.3 可视化指标展示逻辑

在指标展示方面，后端通过 `VisualizationService._build_metrics()` 将不同来源的指标统一映射为前端可展示格式。其中特别强调了两类指标。

第一类为主指标，即 `session_full_match_rate` 与 `message_match_accuracy`，分别对应会话平均匹配率与消息级结构匹配率，用于展示模型对主流程的解释能力。

第二类为参考指标，即 `guard_precision`、`guard_recall` 与 `guard_f1`，用于辅助分析 guard 语义学习质量。系统在实现中明确区分“主指标”和“参考指标”，避免用户将字段级 PRF 误理解为端到端行为正确率。这一设计体现了本文在评估思想上的一致性，也增强了前端展示的可解释性。

## 5.5 本章小结

本章围绕扩展状态机推断系统的评估与可视化设计进行了系统阐述。首先，结合项目中的真实实现说明了实验数据的选择依据、预处理流程以及训练/测试划分策略；其次，针对工业协议流量不完整、严格终态判定失真的问题，构建了由端到端重放、结构匹配、Guard 语义与 Action 语义共同组成的多维评价体系，并从理论与实验两方面说明了其合理性；随后，基于 MODBUS、DNP3 与 IEC104 的实际测评结果，分析了本文模型在控制流恢复方面的优势以及在 guard/action 学习方面仍存在的不足，并通过 Apriori 对比实验与 P-EFSM 结构统计进一步证明了本文方案的改进价值；最后，介绍了基于 FastAPI 的 Web 可视化系统及其核心 API 设计，说明该系统能够将模型训练、指标评估与新流量重放分析集成为统一的交互平台。

总体而言，本章表明本文所提出的扩展状态机推断方法不仅能够在离线实验中恢复工业协议的主行为结构，还具备较好的工程可视化与交互分析能力，为后续系统应用与进一步优化奠定了基础。
